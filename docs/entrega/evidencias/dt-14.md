# DT-14 — orçamento de conexões da API serverless

Origem: revisão Sol de 28/10. Cada instância da API montava Prisma (pool pg padrão, `max 10`), a pool de acesso (`max 5`), a pool da deduplicação MQTT (`max 2`) e o probe (`max 1`): até 18 conexões por instância serverless no Neon, sendo 2 de um recurso que só o worker usa.

## Decisões

| Pergunta | Decisão |
|---|---|
| Quanto cada instância da API pode abrir? | **7** conexões clientes: Prisma 3, pool de acesso 3, probe 1 |
| E o worker? | **7** por réplica: pool de acesso 5 e deduplicação 2 |
| A API precisa da deduplicação? | **Não.** Ela não recebe mensagens do broker; `buildEventDeduplication` é montada só pelo worker |
| O que acontece acima do limite? | O pedido espera uma conexão livre por até 5 s (`POOL_CONNECTION_TIMEOUT_MS`) e depois falha; mais tráfego escala em instâncias novas da Vercel |
| E a consulta já enviada? | Teto de 4 s no cliente (`POOL_QUERY_TIMEOUT_MS`, `query_timeout`), inclusive nas consultas do Prisma (ver abaixo) |
| Como medir em produção? | Cada pool tem um `application_name` (`abp4-api-*`, `abp4-worker-*`) visível no `pg_stat_activity` |

`7N + 8` é o orçamento de **conexões clientes** por instância da API e por réplica do worker — não é o teto do Neon. O teto real depende do compute (`max_connections`) e do PgBouncer do pooler (`default_pool_size = 0,9 × max_connections`, `query_wait_timeout = 120 s`), e a multiplicação por instâncias frias da Vercel não tem limite no código. Cenários, envelope estimado e o que falta verificar em [`docs/guides/deploy.md`](../../guides/deploy.md#orçamento-de-conexões-dt-14).

## Garantia de tempo (o que o código faz)

| Opção | Onde | Valor | O que garante | O que **não** garante |
|---|---|---|---|---|
| `connectionTimeoutMillis` | todas as pools | 5 s (3 s no probe) | desiste de esperar uma conexão livre na pool local | nada sobre a consulta depois de enviada |
| `query_timeout` | pool de acesso, dedup do worker, pool do Prisma (driver adapter) e probe | 4 s (3 s no probe) | o chamador recebe erro mesmo com a consulta parada na fila do pooler | não cancela a consulta no servidor; a conexão segue ocupada até o backend responder |
| `statement_timeout` | — | não configurado | — | — |

`statement_timeout` não entra na conexão porque o `pg` o envia como parâmetro de **startup** e o PgBouncer do Neon aceita só `client_encoding`, `datestyle`, `timezone`, `standard_conforming_strings` e `application_name`; qualquer outro gera `unsupported startup parameter` ([Neon — connection errors](https://neon.com/docs/connect/connection-errors)). Um teto no servidor exigiria `ALTER ROLE ... SET statement_timeout`, que vale para todos os clientes (inclusive a migration do CD) e não foi aplicado. O pior caso documentado portanto é: o pedido falha em ~4 s, e a consulta pode seguir na fila do pooler por até 120 s (`query_wait_timeout`) segurando uma conexão.

O `@prisma/adapter-pg` 7.10 aceita o `PoolConfig` do `pg` e repassa tudo para `new pg.Pool(...)` (`node_modules/@prisma/adapter-pg/dist/index.js`, `connect()`), então `query_timeout` também vale para as consultas do Prisma — que não tem opção própria de timeout de consulta.

## Cobertura

Unitários (`tests/unit/connection-budget.test.ts`):

- os totais fecham em 7 (API) e 7 (worker), e cada fonte tem `application_name` único;
- `buildAccessRuntime` expõe só `pool`, `repository`, `commands`, `decide` e `decider`, com o `max` e o nome pedidos;
- `buildEventDeduplication` monta a pool à parte, com o orçamento do worker;
- toda pool (acesso e deduplicação) tem `connectionTimeoutMillis` e `query_timeout` iguais aos do orçamento;
- `prismaPoolOptions` leva o mesmo `query_timeout` ao pool do Prisma e não inclui `statement_timeout` (que quebraria a conexão com o pooler).

E2E (`tests/e2e/access.e2e.ts` → `DT-14: orcamento de conexoes da API`), com API e worker compilados em processos separados:

1. Dispara 20 pedidos QR e 10 `GET /access-events` de admin em paralelo, com uma cauda artificial de 5,2 s no ramo HTTP, enquanto um NFC entra pelo worker.
2. Amostra o `pg_stat_activity` a cada 20 ms durante a rajada; amostra perdida é ignorada (o pico já acumulado é preservado).
3. Cronometra **só** o ramo MQTT — do `publishAsync` do evento ao `ackStatus` gravado pelo worker; espera o sampler ter coletado antes de começar e o encerra em `finally`.
4. Afirma: todos os 30 pedidos respondem `200`; ACK do NFC é `executed` com ação `open`; pico de `abp4-api-prisma` e `abp4-api-access` entre 1 e 3, probe ≤ 1, soma da API ≤ 7; nenhuma pool de eventos na API; worker dentro de 5 + 2; NFC concluído em menos de 5 s mesmo com o HTTP lento.

O caso "HTTP lento, NFC rápido" é o teste de regressão do cronômetro: com a medição antiga (relógio iniciado antes dos dois ramos) o mesmo cenário falhava com `expected 6437 to be less than 5000`.

## Reprodução

```bash
cd backend
npm ci && npm run db:generate
npm run lint && npm run typecheck && npm run test
npm run build
npm run test:e2e   # sobe PostgreSQL e broker próprios
```

Saída observada em 29/10: unitários `312 passed | 25 skipped`; lint, typecheck e build verdes; E2E `21 passed`.

## Não verificado

- Neon real: nenhuma medição de `pg_stat_activity`, compute ou `max_connections` em produção; os números da documentação são estimativas a conferir.
- Múltiplas instâncias Vercel simultâneas: o E2E usa uma instância da API e um worker.
- Cancelamento no servidor: `query_timeout` é do cliente; não há `statement_timeout` por role configurado.
