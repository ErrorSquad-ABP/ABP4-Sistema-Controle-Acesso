# DT-19 — alinhar capacidade do firmware ao QR assinado

Origem: varredura Sol de 28/10. O backend emite `v1.<terminalId>.<iat>.<exp>.<hmac>` e aceita `terminalId` de até 64 caracteres (`TERMINAL_ID_PATTERN`). Com IDs de 59/60/64 caracteres o token tem 128/129/133 bytes, mas o firmware descartava tudo a partir de 129 (`qr_token::State::token[129]`, `display.cpp`). O terminal ficava sem QR sem nenhum erro visível — diferente da DT-13, acontecia mesmo com a publicação entregue.

## Medição do limite

| Campo | Bytes |
|---|---|
| `v1.` | 3 |
| `terminalId` (máximo do contrato) | 64 |
| separadores (`.`) | 3 |
| `iat` / `exp` (epoch de 10 dígitos, até 2286) | 20 |
| assinatura `base64url(HMAC-SHA-256)` | 43 |
| **total** | **133** |

Token real emitido por `IssueQrCredentialUseCase` com `terminalId` de 64 caracteres:

```
v1.t-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx.1793153400.1793153410.NKjxidR9EvCwa6LoOTT8ftfKSM5J4oGppKQe9QLKZP0
```

## O que mudou

| Arquivo | Mudança |
|---|---|
| `firmware/include/qr_token.h` | `qr_token::kMaxTokenBytes = 133` (derivado do contrato) e `State::token[kMaxTokenBytes + 1]` |
| `firmware/include/display_layout.h` | `kQrByteCapacity = 192` (v8/ECC_LOW, modo byte) e `kQrBufferBytes = 384` |
| `firmware/src/modules/display.cpp` | `drawnToken` no tamanho novo e `static_assert(kMaxTokenBytes <= kQrByteCapacity)` |
| `firmware/tests/test_qr_token.cpp` | cache aceita 133 bytes inteiros |
| `firmware/tests/test_mqtt_command.cpp` | QR de 133 bytes aceito e íntegro; 134 recusado sem apagar o anterior |
| `firmware/tests/test_display_qr.cpp` | encoder real renderiza o token máximo inteiro |
| `.github/workflows/ci-firmware.yml` | compila `qrcode.c` e roda `test_display_qr` |
| `firmware/README.md` | tabela e comandos dos testes host |

`mqtt.cpp` não mudou: o limite continua vindo de `sizeof qrState.token`, que agora vale 134 (133 + terminador).

## Por que o limite é imposto no cache, não no encoder

O encoder (`ricmoo/QRCode`) **não falha** acima da capacidade da versão 8: ele trunca o texto em silêncio (verificado em `test_display_qr`: com 210 bytes, trocar o último caractere não altera nenhum módulo do QR). Por isso:

- o limite de 133 é garantido no cache do firmware (`kMaxTokenBytes`) e no `static_assert` de compilação, não em tempo de execução;
- o `drawnToken` do display usa o mesmo tamanho, então o QR nunca mostra um prefixo truncado;
- o encoder real é exercitado no CI com o token máximo, provando que 133 cabe em v8/ECC_LOW (capacidade 192).

## Reprodução

```bash
cd firmware
pio pkg install -e esp32dev

# testes host (Linux/CI). Em Windows sem g++, rode dentro de um container:
#   docker run --rm -v "$PWD:/work" -w /work gcc:13 bash -lc '<comandos abaixo>'
g++ -std=c++11 -Wall -Wextra -Werror -I include tests/test_qr_token.cpp -o /tmp/t-qr && /tmp/t-qr
gcc -std=c99 -O2 -I .pio/libdeps/esp32dev/QRCode/src -c .pio/libdeps/esp32dev/QRCode/src/qrcode.c -o /tmp/qrcode.o
g++ -std=c++11 -Wall -Wextra -Werror -I include -I .pio/libdeps/esp32dev/QRCode/src \
  tests/test_display_qr.cpp /tmp/qrcode.o -o /tmp/t-display-qr && /tmp/t-display-qr
JSON_SRC=.pio/libdeps/esp32dev/ArduinoJson/src
g++ -std=c++11 -Wall -Wextra -Werror -I tests/fakes -I include -I src -isystem "$JSON_SRC" \
  tests/test_mqtt_command.cpp src/modules/mqtt.cpp -o /tmp/t-mqtt-command && /tmp/t-mqtt-command

pio run   # build do ESP32 com os static_asserts novos
```

Saída observada: `qr_token: validade, relogio e capacidade do maior token OK`, `display_qr: maior token renderizado por inteiro no QR v8 OK`, `mqtt: JSON v1, prazo, dedup, ACK e recusas OK` e `[SUCCESS]` no `pio run` (RAM 14,3%, flash 62,1%).

## Limite conhecido

`kMaxTokenBytes` assume epoch de 10 dígitos (até 2286). O regex do backend aceita 12 dígitos, mas `ValidateQrCredentialUseCase` exige `exp - iat == 10 s`, então nenhum token válido chega a 12 dígitos num horizonte útil.
