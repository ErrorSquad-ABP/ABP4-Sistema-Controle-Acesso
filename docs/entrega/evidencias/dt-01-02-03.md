# DT-01 / DT-02 / DT-03 — acesso seguro e correlação entre processos

Origem: parecer Sol de 21/10, implementação no PR #31. Esta versão é a **integração sobre a `main`** (branch `fix/dt-01-02-03-integracao`), que reaplica as DTs em cima de US-14 (auth JWT), US-19 (QR assinado), US-21 (histórico), US-37 (worker no Render), DT-07 (seed guard) e DT-09 (migrations no CD). A aprovação de colega e os checks remotos continuam exigidos pelo DoD.

## Decisões de integração

- **Auth**: a da `main` (`TokenService`, `requireAuth`, rate limit). O verificador paralelo do PR #31 foi removido; a API autentica com o token do login real.
- **QR**: o protocolo assinado da US-19 (`v1.<terminal>.<iat>.<exp>.<hmac>`), validado por `ValidateQrCredentialUseCase`. O QR opaco, o `TokenHasher` e o model `TerminalQrToken` foram descartados.
- **Worker**: `startWorkerRuntime` valida `ACCESS_MODE`, decisor real e `repository.ready()` antes de `connectBusOrExit`; `worker.ts` e `mqtt-consumer.ts` usam o runtime, sem gate duplicado.
- **Seed**: DT-07 vence — demo somente em banco local e fora de produção. O `terminal-01` demo é criado apenas no caminho demo.
- **CD**: DT-09 vence — `migrate deploy` continua antes do deploy; o E2E foi acrescentado ao CI e ao CD sem remover etapas.
- **Contrato**: `location` anulável, `terminalId` no evento, `requestId` opcional no pedido QR e motivos `UNKNOWN_TERMINAL`/`TERMINAL_INACTIVE`. OpenAPI regenerado.

## Correções obrigatórias do parecer

1. **Atomicidade decisão→comando**: evento, consumo e intenção de comando são gravados na mesma transação (`AccessTransaction.saveCommand`). O `expiresAt` do comando nasce do `occurredAt` do evento; se a janela já venceu, `PublishCommandUseCase` devolve `published: false` e não abre nem cria prazo novo. Regressão: `tests/unit/decide-access.test.ts` ("grava o comando com prazo ancorado no instante da decisao", "falha ao gravar o comando nao devolve concessao…") e `tests/unit/publish-command.test.ts` ("retentativa depois da janela nao publica abertura nem cria prazo novo").
2. **Idempotência do pedido QR**: `requestId` estável no corpo do pedido vira o id do evento. Repetir devolve o mesmo evento e o mesmo comando, sem consumir a autorização de novo. Regressão: `tests/unit/request-qr-access.test.ts` ("repetir o mesmo requestId devolve o mesmo evento e o mesmo comando", "repetir apos falha de publicacao nao consome a autorizacao de novo") e o cenário HTTP no E2E.
3. **Auth**: verificador paralelo removido; `requireAuth` e o token do login.
4. **QR**: validação por `ValidateQrCredentialUseCase`; sem hash nem `TerminalQrToken`.
5. **Gate no runtime**: coberto nos dois entry points (unit + E2E).
6. **E2E**: seed demo preparada com `NODE_ENV=development` em banco descartável; API e worker sobem em `NODE_ENV=production`; login real → pedido QR → MQTT → ACK → histórico.

## Reprodução sem administrador

Pré-requisito: Node 24+ e acesso ao npm para instalar dependências. Não precisa Docker, serviço de Windows, elevação ou instalação global.

```bash
cd backend
npm ci
npm run db:generate
npx prisma validate
npm run lint
npm run typecheck
npm run test:coverage
npm run test:e2e
npm run build
npm run openapi:generate
```

`test:e2e` compila o backend e inicia:

1. PostgreSQL nativo temporário (`embedded-postgres`), porta livre em loopback e diretório exclusivo no temporário do usuário.
2. Migrations reais, comparação banco/schema sem drift e seed demo duas vezes (fora de produção).
3. Broker MQTT Aedes em porta TCP livre de loopback.
4. API HTTP e worker compilados, em processos independentes e fusos distintos, com `NODE_ENV=production` e modo real.
5. Terminal simulado usando `SimulatedTerminal` e mensagens MQTT v1 com QoS 1.

O harness usa o próprio banco, ignora o `.env` e encerra processos e dados ao terminar. Em Linux, roda com usuário comum, como no GitHub Actions.

## Cenários E2E

- Produção sem decisor, produção com `ACCESS_MODE=demo` e banco sem migrations encerram antes de conectar ao broker.
- Demo explícito sobe em desenvolvimento sem banco, com aviso.
- Identificador inválido de terminal e local inexistente são rejeitados pelas constraints.
- Terminal desconhecido recebe `deny`; evento com identificador e local nulo é consultável por administrador.
- NFC conhecido valida credencial e autorização do local e correlaciona o ACK.
- QR emitido pelo worker é validado pela API, que publica o comando persistido; o worker correlaciona o ACK do simulador.
- Repetir o mesmo `requestId` mantém evento e comando e consome um único uso.
- QR inválido, expirado e posição fora do raio são negados e auditados sem comando de abertura.
- Terminal desativado nega QR válido.
- Comando originado na API é correlacionado após reinício do worker, inclusive com status `expired`.
- Histórico exige JWT do login; usuário comum recebe 403 na rota global.

## Limites da validação

O E2E valida o backend compilado, PostgreSQL e MQTT TCP reais com terminal emulado; não prova atuação física de servo, câmera/GPS de aparelho ou TLS do ESP32. A correlação usa persistência compartilhada; não há fila outbox nem retentativa automática de publicações. ACK é independente da decisão de autorização e registra o resultado relatado pelo terminal.

Migrations de produção devem ser aplicadas antes de iniciar o consumidor real, com o mesmo banco configurado na API e no worker.
