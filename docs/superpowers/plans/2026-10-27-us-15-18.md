## Contexto

- Contrato já existe em `operations.ts`/schemas para `users` e `authorizations`; as rotas ainda são stubs 501.
- Cards:

  - US-18: "Usuário consulta as próprias autorizações."

## Escopo
1. **US-15** — `GET /users`, `POST /users`, `GET /users/:id`, `PATCH /users/:id`, `DELETE /users/:id` (ADMIN).
2. **US-18** — `GET /me/authorizations` (autenticado), com paginação e filtro `status`.
3. **US-32** — sem código: o E2E de acesso já roda em `ci-backend`/`cd-backend`; fechar com evidência.

## Regras de negócio
- Papéis: ADMIN, RESIDENT, VISITOR (já no schema).
- E-mail normalizado (schema faz lowercase); duplicado → 409.
- Senha: hash scrypt com `newPasswordSalt()`; nunca retornar `passwordHash`.
- `DELETE` é exclusão lógica: `active=false`, histórico preservado → 204.
- `PATCH active:false` desativa; não pode haver auto-bloqueio? Não exigido — permitir, mas o token do admin segue válido até expirar (middleware recarrega e nega usuário inativo).
- Autorização → status calculado:
  - CANCELED se `canceledAt != null`
  - SCHEDULED se `now < startsAt`
  - EXPIRED se `now >= endsAt` ou `usedCount >= maxUses`
  - ACTIVE caso contrário
  - `remainingUses = max(0, maxUses - usedCount)`
- Filtro `status` do `/me/authorizations` aplica sobre o status calculado.
- Paginação `{items,page,pageSize,total}`; ordenação `startsAt desc, id desc`.
