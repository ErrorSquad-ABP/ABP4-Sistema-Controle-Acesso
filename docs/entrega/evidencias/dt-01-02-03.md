# DT-01 / DT-02 / DT-03 — acesso seguro e correlação entre processos

Origem: parecer Sol de 21/10. Implementação local e evidências de 26/10/2026. Sprint alvo permanece decisão da Planning 2. A aprovação de colega e os checks remotos continuam exigidos pelo DoD para concluir os cards.

## Escopo entregue

| Card | Comportamento | Teste principal |
|---|---|---|
| DT-01 | Modo real padrão; demo explícito somente fora de produção; falha antes do MQTT sem decisor/banco migrado | `tests/unit/access-safety.test.ts`, boot dos processos no E2E |
| DT-02 | Comando persistido antes do envio; API/worker compartilham PostgreSQL; ACK atômico por comando/terminal; sobrevive a reinício | `tests/unit/publish-command.test.ts`, API QR → MQTT → simulador → ACK no E2E |
| DT-03 | Terminal cadastrado com FK de local e formato validado; decisor usa o local; desconhecido negado e consultável com local nulo | `tests/unit/access-policy.test.ts`, `decide-access.test.ts`, histórico HTTP no E2E |

Para demonstrar integralmente os aceites, foi necessária uma fatia de decisão real NFC/QR e consulta de eventos. As três rotas de `access-events` funcionam com banco e `JWT_SECRET`. Autenticação valida JWT HS256 e consulta perfil/atividade do usuário no banco; login e demais CRUDs permanecem nas stories correspondentes. Isso não conclui integralmente US-14, US-19, US-20 ou US-21.

O aceite de terminal desconhecido também exigiu a compatibilidade de evento sem local: `location` anulável, `terminalId` preservado e motivos `UNKNOWN_TERMINAL`/`TERMINAL_INACTIVE`. O OpenAPI foi regenerado. O mobile atual não consome o histórico; a futura integração deve tratar esses casos.

## TDD e correções verificadas

Os testes de seleção segura, comando compartilhado, política de local e contrato foram escritos antes das respectivas implementações. O primeiro ciclo mostrou módulos ausentes e a rejeição de evento com local nulo. Depois da implementação, os cenários unitários passaram.

O E2E inicialmente mostrou um `500` ao negar uma posição a milhares de quilômetros: `distanceMeters` usava `Decimal(8,2)`. A migration amplia para `Decimal(10,2)`, permitindo persistir a negativa. O cenário de requestId reutilizado por outro terminal também foi observado falhando antes da proteção contra colisão e passou após a correção.

O fluxo de retentativa agora preserva comando e prazo quando a publicação falha, porque uma falha de transporte não prova ausência de entrega. Consumo de autorização e evento são transacionais; concorrência no último uso permite uma única concessão. ACK duplicado não sobrescreve o resultado anterior.

O E2E também executa API em `America/Sao_Paulo` e worker em `UTC`. Esse cenário expôs interpretação local de `TIMESTAMP` sem fuso pelo driver: afetava validade do QR, janela de autorização e histórico. A borda SQL agora interpreta esses campos em UTC, grava datas ISO UTC e normaliza filtros com offset antes da consulta. O teste confere o instante do evento e a consulta por período `-03:00`.

## Reprodução sem administrador

Pré-requisito: Node 24+ e acesso ao npm para instalar dependências. Não precisa Docker, serviço de Windows, elevação ou instalação global.

```bash
cd backend
npm ci
npm run db:generate
npm run lint
npm run typecheck
npm run test:coverage
npm run test:e2e
npm audit
```

`test:e2e` compila o backend e inicia:

1. PostgreSQL nativo temporário, baixado por `embedded-postgres`, com porta livre em loopback e diretório exclusivo no temporário do usuário.
2. Migrations reais; comparação banco/schema Prisma sem diferenças; seed executada duas vezes.
3. Broker MQTT Aedes em uma porta TCP livre de loopback.
4. API HTTP e consumidor MQTT compilados, em processos independentes e fusos distintos, com `NODE_ENV=production` e modo real.
5. Terminal simulado usando a classe `SimulatedTerminal` do projeto e mensagens MQTT v1 com QoS 1.

O harness usa seu próprio banco, ignora os valores de conexão do `.env` e encerra seus processos e dados ao terminar. Em Linux, executa com usuário comum, como no GitHub Actions; não cria usuários nem requer sudo. As chaves e identidades do teste são exclusivas do banco descartável.

## Cenários E2E

- Produção sem decisor e produção com demo encerram com erro antes de conectar ao broker.
- Demo explícito inicia em desenvolvimento sem banco.
- Banco sem migrations impede inicialização do consumidor.
- Identificador inválido e local inexistente são rejeitados pelas constraints.
- Terminal desconhecido recebe `deny`; evento com identificador e local nulo é consultável por administrador.
- NFC conhecido valida credencial e autorização do local e correlaciona o ACK.
- QR emitido pelo worker é validado pela API, que cria comando; o worker recebe e correlaciona o ACK do simulador.
- QR inválido, expirado e posição fora do raio são negados e auditados sem comando de abertura.
- JWT ausente, assinatura inválida e token expirado recebem 401; usuário comum recebe 403 no histórico global.
- ACK de outro terminal não consome pendência; atualizações concorrentes resultam em uma correlação; duplicata não altera o resultado.
- Comando originado na API é correlacionado após reinício do worker, preservando inclusive status `expired`.
- Alterar o local do terminal impede usar autorização do local anterior.
- Terminal desativado gera negativa auditada.
- Requisições simultâneas disputando o último uso geram uma concessão e uma negativa.
- Instantes e filtros por período com offset preservam UTC mesmo com API/worker em fusos diferentes.

## Limites da validação

Resultado final local (Windows, Node 24, sem elevação): **154 testes unitários/integração e 15 cenários E2E passaram**. Lint, typecheck, build, validação Prisma, migrations/schema, seed repetida e `git diff --check` passaram. `npm audit` reportou zero vulnerabilidades após atualizar `body-parser` e `fast-uri` dentro das faixas já permitidas no lockfile.

A cobertura da suíte unitária/Supertest foi 71,16% de linhas e 78,35% de branches. Esse relatório inclui código gerado e não instrumenta os subprocessos do E2E; adapters de banco, MQTT e rotas reais também foram exercitados pelo E2E separado. Os workflows CI e CD agora executam esse E2E antes das etapas seguintes; checks remotos ainda não foram executados nesta entrega local.

O E2E valida o backend compilado, PostgreSQL e MQTT TCP reais com terminal emulado; não prova atuação física de servo, câmera/GPS de aparelho ou TLS do ESP32. A correlação usa persistência compartilhada; não há fila outbox nem retentativa automática de publicações. ACK é independente da decisão de autorização e guarda o resultado relatado pelo terminal.

Migrations de produção devem ser aplicadas antes de iniciar o consumidor real, com o mesmo banco configurado na API e no worker. O teste local não publica serviços externos nem substitui review independente e CI remoto.
