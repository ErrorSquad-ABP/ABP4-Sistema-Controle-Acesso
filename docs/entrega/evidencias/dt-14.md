# DT-14 — orçamento de conexões da API serverless

Origem: revisão Sol de 28/10. Cada instância da API montava Prisma (pool pg padrão, `max 10`), a pool de acesso (`max 5`), a pool da deduplicação MQTT (`max 2`) e o probe (`max 1`): até 18 conexões por instância serverless no Neon, sendo 2 de um recurso que só o worker usa.

## Decisões

| Pergunta | Decisão |
|---|---|
| Quanto cada instância da API pode abrir? | **7**: Prisma 3, pool de acesso 3, probe 1 |
| E o worker? | **7** em instância única: pool de acesso 5 e deduplicação 2 |
| A API precisa da deduplicação? | **Não.** Ela não recebe mensagens do broker; `buildEventDeduplication` é montada só pelo worker |
| O que acontece acima do limite? | O pedido espera uma conexão livre por até 5 s (`POOL_CONNECTION_TIMEOUT_MS`) e depois falha; mais tráfego escala em instâncias novas da Vercel |
| Como medir em produção? | Cada pool tem um `application_name` (`abp4-api-*`, `abp4-worker-*`) visível no `pg_stat_activity` |

Total no Neon: `7 × instâncias ativas da API + 7 (worker) + 1 (migration do CD)`. Tabela completa e consulta de conferência em [`docs/guides/deploy.md`](../../guides/deploy.md#orçamento-de-conexões-dt-14).

## O que mudou

| Arquivo | Mudança |
|---|---|
| `backend/src/main/config/connection-budget.ts` | orçamento por processo e por fonte (`max` + `application_name`) e timeout de espera |
| `backend/src/main/access-composition-root.ts` | `buildAccessRuntime` recebe o orçamento e não cria mais a deduplicação; nova `buildEventDeduplication` |
| `backend/src/main/composition-root.ts` | API usa `API_CONNECTIONS`; `close()` encerra também o Prisma |
| `backend/src/main/mqtt/worker-runtime.ts` | worker monta acesso e deduplicação com `WORKER_CONNECTIONS` e encerra as duas pools |
| `backend/src/infrastructure/database/prisma-client.ts` | limites opcionais do pool do Prisma (sem eles, padrão do pg para testes e scripts) |
| `backend/src/infrastructure/database/postgres-database-probe.ts` | `application_name` no probe |
| `backend/tests/e2e/fixtures/dt05-worker.mjs` | usa a nova separação |
| `docs/guides/deploy.md` | seção "Orçamento de conexões" e correção da frase que dizia que o worker não acessa o banco |

## Cobertura

Unitários (`tests/unit/connection-budget.test.ts`):

- os totais fecham em 7 (API) e 7 (worker), e cada fonte tem `application_name` único;
- `buildAccessRuntime` expõe só `pool`, `repository`, `commands`, `decide` e `decider`, com o `max` e o nome pedidos;
- `buildEventDeduplication` monta a pool à parte, com o orçamento do worker.

E2E (`tests/e2e/access.e2e.ts` → `DT-14: orcamento de conexoes da API`), com API e worker compilados em processos separados:

1. Dispara 20 pedidos QR e 10 `GET /access-events` de admin em paralelo, enquanto um NFC entra pelo worker.
2. Amostra o `pg_stat_activity` a cada 20 ms durante a rajada.
3. Afirma: todos os 30 pedidos respondem `200`; pico de `abp4-api-prisma` e `abp4-api-access` entre 1 e 3, probe ≤ 1, soma da API ≤ 7; nenhuma pool de eventos na API; worker dentro de 5 + 2; o NFC recebe comando em menos de 5 s.

